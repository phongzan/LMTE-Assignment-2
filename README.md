# Flux language interpreter

Flux is a C++17 tree-walking interpreter for a dynamically typed language with
built-in variable history. This README gives the complete installation,
operation and testing procedure expected by the assessment rubric.

## 1. Prerequisites

Install:

- CMake 3.16 or newer;
- a C++17 compiler;
- on Windows, Visual Studio 2022 Build Tools with **Desktop development with
  C++** and a Windows SDK.

No third-party C++ libraries are required.

### VS Code Setup (Optional)

If opening this project in VS Code:
1. Install the C/C++ extension (by Microsoft)
2. The project includes `.vscode/c_cpp_properties.json` with proper configuration
3. VS Code will auto-configure IntelliSense for your compiler
4. If you see red squiggly lines: these are IntelliSense-only cosmetic issues and do NOT affect compilation or tests
5. The project compiles and tests successfully regardless of IntelliSense status

## 2. Configure and build

Open a terminal in the repository root and compile with g++:

```powershell
g++ -std=c++17 -O2 -Wall -I include src/Lexer.cpp src/Parser.cpp src/SemanticAnalyzer.cpp src/Interpreter.cpp src/Environment.cpp src/Value.cpp src/Operators.cpp src/Token.cpp src/CodeGen.cpp src/VM.cpp main.cpp -o flux.exe
```

Executable will be `flux.exe` in the current directory.

### VS Code

The repository contains `.vscode/settings.json` for IntelliSense configuration.

Compile from terminal as shown above, or integrate the g++ command into your editor.

## 3. Run a Flux program

Windows:

```powershell
./build/Debug/flux.exe examples/stock_ledger.flx
```

macOS/Linux or a single-configuration build:

```bash
./build/flux examples/stock_ledger.flx
```

Expected stock example output:

```text
45
[50, 45]
```

### CLI Flags

- **`flux <program.flx>`** — Execute a Flux program from file (default tree-walking interpreter)
- **`flux --mem <program.flx>`** — Execute with memory instrumentation (prints array allocation stats)
- **`flux --tokens <program.flx>`** — Dump lexer output (tokenization stage)
- **`flux --ast <program.flx>`** — Dump parser output (syntax analysis stage)
- **`flux --bytecode <program.flx>`** — Dump generated bytecode (code generation stage)
- **`flux --vm <program.flx>`** — Execute using bytecode VM (experimental)

**Demonstration of all 4 compilation stages:**

```bash
# Stage 1: Lexical Analysis
./flux --tokens examples/stock_ledger.flx

# Stage 2: Syntax Analysis  
./flux --ast examples/stock_ledger.flx

# Stage 3: Code Generation (produces bytecode)
./flux --bytecode examples/stock_ledger.flx

# Stage 4: Execution (tree-walking interpreter or bytecode VM)
./flux examples/stock_ledger.flx                 # Tree-walking
./flux --vm examples/stock_ledger.flx            # Bytecode VM (with --bytecode dump)
```

**Optimizations implemented:**
- **Constant folding**: Compile-time evaluation of constant expressions (e.g., `2 + 3 * 4` → `14`)
- **Dead code elimination**: Removal of unreachable code after `give` statements (code generation optimization)
- Short-circuit evaluation for `and`/`or` operators via conditional jumps

### CLI Exit Codes

- **0** — Successful execution
- **64** — Invalid command-line usage (wrong number of arguments)
- **65** — Compilation error (lexical, syntax, or semantic)
- **66** — File I/O error (cannot open program file)
- **70** — Runtime error (undefined variable, type mismatch, division by zero, etc.)

Compilation diagnostics are written to **stderr**; program output to **stdout**.

## 4. Language syntax

Each statement occupies one logical line, braces enclose blocks and `#` begins a
comment.

```text
42 -> quantity                 # mutable variable
0.1 => GST                    # constant
quantity + 5 -> quantity      # arithmetic update

when quantity < 10 {
    show "low"
} otherwise {
    show "ok"
}

repeat 4 as i { show i }
until quantity > 100 { quantity * 2 -> quantity }
each item in [1, 2, 3] { show item }

fn double(value) { give value * 2 }
5 then double then show
```

### Arrays

Arrays are zero-based, may be nested and may contain mixed types.

```text
[[1, 2], [3, 4]] -> matrix
99 -> matrix[0][1]
push(matrix, [5, 6]) -> matrix
show len(matrix)
```

### History and rewind

```text
10 -> stock
20 -> stock
show stock~1          # 10
show history(stock)  # [10, 20]
rewind stock          # current value becomes 10
```

### Scope and closures

Function writes are local unless marked `outer`. Nested functions retain their
declaration environment, which provides closure behaviour.

## 6. Run all provided tests

```powershell
ctest --test-dir build -C Debug --output-on-failure
```

This runs the lexer/parser, semantic, runtime, interpreter and CLI golden-file
suites. A feature is complete only when CTest reports `100% tests passed`.

### Test Suite Structure

**Unit Tests** (written in C++):
- `tests/frontend_tests.cpp` (~48 tests) — Lexer tokenization, parser AST construction, syntax error recovery
- `tests/semantic_tests.cpp` (~13 tests) — Semantic validation rules (constants, scope, types, outer writes)
- `tests/runtime_tests.cpp` (~26 tests) — Value operations, environment/history, built-in operators
- `tests/interpreter_tests.cpp` (~47 tests) — End-to-end Flux program execution

**Golden File Tests** (48 planned test cases):
- `tests/pass/p*.flx` + `.expected` — Valid programs (P1-P23) and expected output
  - P1: Literals and arrays
  - P2-P3: Arithmetic operators and precedence
  - P4: Constants and immutability
  - P5-P6: Comparison, Boolean logic, and selection
  - P7-P9: Three loop forms (repeat, until, each)
  - P10-P13: Functions, recursion, closures, and scope rules
  - P14-P19: Arrays, history, rewind, and user input
  - P20-P23: Integration tests (stock ledger, bubble sort, dead code, memory)

- `tests/fail/e*.flx` + `.expected` — Invalid programs (E1-E25) and expected error diagnostics
  - E1-E8: Lexical, syntax, and panic-mode recovery errors
  - E9-E14: Semantic errors (constants, scope, types, outer writes)
  - E15-E25: Runtime errors (undefined variables, type mismatches, division by zero, array indexing, etc.)

CTest auto-discovers all `.flx` files in `tests/pass/` and `tests/fail/` and registers them automatically.
To add a new test case, simply create `tests/pass/pNN_description.flx` and `tests/pass/pNN_description.expected`
and rebuild with CMake.

## 7. Add or modify a bespoke test

### Fast component/interpreter test

Add a case to the relevant file:

- `tests/frontend_tests.cpp` for token or AST behaviour;
- `tests/semantic_tests.cpp` for pre-execution rules;
- `tests/runtime_tests.cpp` for `Value`, `Environment` or operators;
- `tests/interpreter_tests.cpp` for a complete in-memory Flux program.

Rebuild and run CTest after changing a C++ test.

### End-to-end golden test

1. Copy an existing program in `tests/pass` or `tests/fail`.
2. Edit the `.flx` source using the syntax above.
3. Edit the matching `.expected` file. Successful tests compare standard output;
   failing tests compare standard error and require a non-zero exit code.
4. Register the pair with `add_flux_golden_test(...)` in `CMakeLists.txt`.
5. Reconfigure, build and run CTest.

The CMake runner normalizes Windows and Unix line endings before performing an
exact comparison.

## 9. Compiler Architecture: Tree-Walking vs Bytecode

### Execution Models

**Default: Tree-Walking Interpreter**
```
Source → Lexer → Tokens → Parser → AST → Interpreter → Output
```
- Direct AST traversal and execution
- Simplest model, full feature support
- Used for standard `flux <program.flx>` execution

**Bytecode VM (Experimental)**
```
Source → Lexer → Tokens → Parser → AST → CodeGen → Bytecode → VM → Output
```
- Four-stage compiler pipeline (all required stages present)
- Stack-based virtual machine execution
- Code generation enables optimizations
- Used with `flux --vm <program.flx>` or `flux --bytecode <program.flx>`

### Code Generation & Optimization

**Constant Folding**
- Compile-time evaluation of constant expressions
- Example: `2 + 3 * 4` compiled to bytecode instruction `PUSH 14` (not `PUSH 2 PUSH 3 PUSH 4 MUL ADD`)
- Reduces runtime computation, improves performance

**Dead Code Elimination**
- Removes unreachable code after `give`/`return` statements
- Cleans up bytecode, reduces code size
- Enabled automatically during bytecode generation

**Short-Circuit Evaluation**
- `and`/`or` operators use conditional jumps
- Avoids evaluating unnecessary operands
- Implemented via `JUMP_IF_FALSE` instruction

## 10. Implemented assessment features

- tokenisation and lexical analysis;
- recursive-descent syntax analysis and panic-mode recovery;
- semantic analysis and dynamic runtime type checking;
- variables, constants and literals;
- arithmetic, comparison and Boolean logic;
- selection, three forms of iteration, functions and recursion;
- nested arrays and scope chains;
- closures and reference-counted dynamic memory;
- domain-specific variable history, rewind and pipelines;
- **code generation (bytecode compiler)** with optimization passes;
- **stack-based virtual machine** for executing bytecode;
- automated component, integration and CLI tests.

Flux supports two execution models:
1. **Tree-walking interpreter** (default) - executes AST directly
2. **Bytecode VM** (experimental) - compiles to bytecode then executes

Both are fully functional alternatives; the assignment brief permits either approach.
